# Paper Writing Context And Outline

Working title:

Provenance-Aware Cooperative Knowledge Graph Reasoning for Vehicle-to-Vehicle Autonomous Driving

Alternative titles:

- Explicit Cooperative Scene Graphs for V2V Driving Reasoning
- Knowledge-Graph-Based Cooperative Scene Reasoning under Occlusion
- From Cooperative Perception to Structured Reasoning: A Provenance-Aware KG Layer for V2V Driving

This document is a paper-starting artifact. It is not the final paper text. It organizes the motivation, approach, architecture, fusion strategy, confidence modeling, evaluation protocol, current results, limitations, and references so that a clean manuscript can be written from it.


1. One-Sentence Summary
=======================

We build an explicit provenance-aware and uncertainty-aware knowledge-graph reasoning layer for cooperative autonomous driving, where each connected vehicle contributes structured scene facts, the system fuses them into a cooperative graph, and benchmark-style driving questions are answered through deterministic graph reasoning rather than only through implicit feature fusion or free-form language-model reasoning.


2. Central Research Claim
=========================

The main claim should not be simply "we use a graph." A stronger and more defensible claim is:

Existing cooperative perception and V2V reasoning systems often fuse information implicitly, either through feature-level neural fusion or through multimodal LLM prompting. Our approach makes the intermediate world model explicit. It represents objects, visibility, relations, provenance, candidate hypotheses, confidence, uncertainty, and conflict as structured graph facts. This makes cooperative reasoning more inspectable, reproducible, and easier to evaluate under partial observability and occlusion.


3. Motivation
=============

Autonomous vehicles are limited by local sensing. A single vehicle can miss objects because of occlusion, limited range, blind spots, sensor noise, and viewpoint-specific ambiguity. Vehicle-to-vehicle cooperation helps because another vehicle may observe the same scene from a different viewpoint.

However, cooperation introduces its own problem: information from multiple vehicles must be aligned, trusted, fused, and reasoned over. Many cooperative perception methods focus on improving detection or tracking through early, intermediate, or late fusion, but the resulting representation is often difficult to inspect at the level needed for question answering and planning-aware reasoning.

The motivation for this work is therefore:

- preserve what each vehicle independently knows;
- fuse complementary evidence without losing provenance;
- distinguish supported objects from weaker candidates;
- reason explicitly about visibility, occlusion, and trajectory relevance;
- expose confidence and uncertainty instead of hiding them inside a black-box model;
- evaluate whether a deterministic graph-reasoning layer can support benchmark-style cooperative driving QA.

The strongest safety motivation is occlusion: if the ego vehicle cannot see a relevant object but another connected vehicle can provide evidence, the fused cooperative graph should make that object available to downstream reasoning.


4. Problem Setting
==================

Input:

- synchronized V2V driving scenes from the V2V4Real / V2V-GoT ecosystem;
- two connected vehicles in the current implementation;
- per-agent observations or processed prediction arrays;
- object positions, object IDs, object types, confidence scores, and visibility facts where available;
- future ego trajectory or planned path context;
- benchmark QA records from V2V-GoT-QA.

Output:

- benchmark-compatible answers for V2V-GoT-QA task families;
- intermediate graph artifacts that can be inspected and compared;
- object selections with confidence, provenance, and relation-based rationale.

Current task families supported end to end:

- Q1 / notable_objects;
- Q2 / occluding_objects;
- Q3 / invisible_objects;
- Q4 / planning_awareness;
- Q5 / object_motion_prediction;
- Q6 / agent_motion_prediction;
- Q8 / control_settings;
- Q9 / future_trajectory.

The first paper should focus most heavily on Q1-Q4 because these are the strongest match to the current graph reasoning contribution: object selection, visibility, occlusion, and planning awareness.


5. Proposed Approach
====================

The proposed framework has six main stages.

Stage 1: Multi-Agent Scene Input
--------------------------------

Each benchmark sample is mapped to a timestamped cooperative scene. The scene contains the asking agent, partner vehicle context, future trajectory, processed object observations, confidence scores, and visibility labels when available.

Motivation:

This stage keeps the work grounded in a real cooperative perception benchmark instead of a hand-authored toy scene.

Stage 2: Local Graph Construction
---------------------------------

Each vehicle can be projected into a local graph. A local graph contains only the evidence available to one vehicle. It includes:

- object tracks;
- object positions;
- object type;
- object confidence;
- visibility facts for that agent;
- ego-relative spatial relations;
- provenance of the observations;
- supported/candidate status;
- uncertainty and conflict scores.

Motivation:

The local graph is the single-agent control condition. Without it, cooperative gains cannot be interpreted. It also ensures that fusion errors do not hide local graph construction errors.

Stage 3: Cross-Agent Association
--------------------------------

Observations from different agents are matched conservatively. The current association logic compares:

- source agent identity;
- object type;
- 2D position distance;
- a maximum distance threshold.

For a matched pair, association confidence is derived from geometric closeness:

confidence = 1 - distance / max_distance

clamped into [0, 1].

Motivation:

This gives a simple, inspectable matching rule. It avoids aggressive over-merging and preserves uncertainty when two observations may not represent the same physical object.

Stage 4: Cooperative Support Enrichment
---------------------------------------

When a cross-agent matched observation corresponds to an already-supported track, the counterpart observation is attached as additional evidence. The object track provenance is updated with:

- source agent IDs;
- observation IDs;
- latest timestamp index;
- attached observations.

Motivation:

This turns cooperation into explicit evidence support rather than opaque averaging. A graph node can now show which vehicle supported it and which observations contributed to it.

Stage 5: Relation And Visibility Construction
---------------------------------------------

The graph derives relation facts such as:

- front_of;
- behind;
- left_of;
- right_of;
- near;
- near_trajectory;
- near_first_waypoint;
- path_relevant;
- cooperatively_supported;
- low_conflict.

Relations have confidence values. Some are deterministic geometric relations with confidence 1.0; others are proximity-derived or support-derived.

Visibility facts are loaded from processed assets when available, and otherwise inferred conservatively. Candidate-only tracks are not marked visible unless their confidence passes a threshold.

Motivation:

Most benchmark questions are not raw detection questions. They ask about visible, invisible, occluding, or planning-relevant objects. Explicit relations and visibility facts make these queries deterministic and explainable.

Stage 6: Task-Specific Graph Reasoning
--------------------------------------

V2V-GoT-QA questions are routed to task handlers. Each handler performs deterministic graph selection, ranking, thresholding, and answer rendering.

Examples:

- notable_objects: select visible objects near the planned trajectory and prefer grounded/supported objects;
- occluding_objects: rank visible blockers using pairwise and risk-adaptive evidence;
- invisible_objects: select hidden or invisible notable objects using graph features and, in the latest experiments, a train-selected logistic acceptor over a broader candidate pool;
- planning_awareness: combine at most one hidden relevant object and at most one visible notable object to match the benchmark answer shape;
- future_trajectory: render planned trajectory points;
- control_settings: render speed/steering-style action guidance;
- object_motion_prediction: use adjacent-frame object-track velocity when available;
- agent_motion_prediction: use nonzero CAV pose velocity when available, otherwise planned trajectory direction.

Motivation:

The graph gives shared structured evidence, but each task has a different output contract. Keeping task handlers separate makes evaluation, ablation, and failure analysis cleaner.

7. How Information Is Fused
===========================

The fusion strategy is deliberately conservative and provenance-preserving.

Current fusion logic:

1. Load per-agent evidence for the same timestamp.
2. Build or update object tracks from grounded GT/prediction evidence.
3. Create candidate tracks for weaker predictions rather than discarding them.
4. Associate observations across agents if they are close in position and share object type.
5. Attach cross-agent support to existing tracks when a match is plausible.
6. Preserve unmatched or weak evidence as candidates instead of forcing a merge.
7. Derive relation facts and visibility facts after object tracks are populated.
8. Let task-level handlers decide which objects are relevant for a question.

Why this matters:

- It avoids premature collapse of uncertain evidence.
- It preserves source identity.
- It allows later queries to ask whether an object is single-agent, multi-agent, candidate-only, or cooperatively supported.
- It gives a direct route for failure analysis: wrong answer can be traced to missing candidate, wrong association, wrong relation, wrong threshold, or wrong rendering.


8. Confidence And Trust In The Knowledge Graph
==============================================

The graph does not currently use one single global "KG confidence" number. Confidence is represented at multiple levels:

Object confidence:

- inherited from perception or GT-derived support;
- used directly in task scoring;
- higher object confidence usually means stronger evidence for keeping the object.

Association confidence:

- derived from cross-agent geometric agreement;
- high when same-type observations from different vehicles are close together;
- low or absent when observations cannot be safely matched.

Relation confidence:

- deterministic relations such as front/behind/left/right can be confidence 1.0;
- near/path relations use distance-based confidence;
- cooperatively_supported confidence increases with number of source agents;
- low_conflict confidence is derived from 1 - conflict_score.

Visibility confidence:

- processed visibility labels are preserved when available;
- inferred visibility is conservative;
- candidate-only visibility requires a confidence threshold.

Uncertainty and conflict:

- uncertainty_score represents unresolved or lower-quality evidence;
- conflict_score represents disagreement or risk of inconsistent tracks;
- task rankers can penalize high uncertainty or high conflict.

Acceptor model confidence:

- for invisible_objects, train-derived logistic/MLP acceptors can output a probability-like acceptance score;
- current results show logistic acceptors generalize better than MLP as a primary selector;
- MLP overfitting is controlled with split discipline, L2 regularization, small architecture, and early stopping, but the current MLP did not outperform logistic regression.

Paper phrasing:

Rather than claiming the graph is absolutely correct, say that the KG carries calibrated evidence channels: object confidence, provenance support, relation confidence, visibility facts, uncertainty, and conflict. The decision policy then combines these channels for each task.


9. Architecture Diagram In Words
================================

A manuscript figure can show this pipeline:

V2V4Real / V2V-GoT processed scene
    -> per-agent observations and visibility facts
    -> local graph construction for ego and partner
    -> cross-agent association
    -> provenance-aware support enrichment
    -> cooperative knowledge graph
    -> deterministic query/ranking handlers
    -> V2V-GoT-QA answer export
    -> official-style QA evaluation

The figure should visually emphasize that the KG sits between perception outputs and QA/planning reasoning.


10. Evaluation Strategy
=======================

The evaluation should be described as a sequence, not as one monolithic score.

Evaluation Step 1: Task Inventory
---------------------------------

Purpose:

Identify all benchmark task families and decide which are supported first.

Outcome:

The V2V-GoT-QA benchmark contains:

- notable_objects;
- occluding_objects;
- invisible_objects;
- planning_awareness;
- object_motion_prediction;
- agent_motion_prediction;
- control_settings;
- future_trajectory.

Q1-Q4 were prioritized first because they directly evaluate object, visibility, occlusion, and planning-aware graph reasoning.

Evaluation Step 2: Smoke-Level Support
--------------------------------------

Purpose:

Check that each task family runs end to end and does not silently fail.

Metrics:

- supported sample count;
- unsupported sample count;
- parse errors;
- output generation success.

Interpretation:

This is not final performance evaluation. It only proves benchmark-path coverage.

Evaluation Step 3: Local Proxy Scoring
--------------------------------------

Purpose:

Rapidly compare candidate policies during development.

Metrics:

- object-level precision;
- object-level recall;
- object-level F1;
- exact-match count;
- difference between cooperative and ego-only outputs.

Interpretation:

Useful for debugging and iteration, but not enough for final paper claims unless aligned with official evaluation.

Evaluation Step 4: Official-Style Export And Scoring
----------------------------------------------------

Purpose:

Convert deterministic KG predictions back into V2V-GoT-style answer records and run the upstream/simplified official QA evaluator.

Metrics for Q1-Q4:

- binary precision/recall/F1;
- localization precision/recall/F1 at thresholds 0.5, 1.0, 2.0, and 4.0 meters;
- output parse error rate;
- GT parse error rate.

Interpretation:

This is the most paper-facing evaluation path for Q1-Q4. Any claim should specify whether it is official-style and whether it is full validation or a slice.

Evaluation Step 5: Train/Validation Discipline
----------------------------------------------

Purpose:

Avoid overfitting thresholds and policies to validation.

Protocol:

- train split is used for diagnosis, policy development, threshold selection, and ablations;
- validation split is reserved for reporting selected policies;
- Q3 invisible_objects policy experiments should be selected on train and only then promoted to validation.

Evaluation Step 6: Failure Analysis
-----------------------------------

Purpose:

Turn metrics into actionable improvements.

Examples:

- Q2 occluding_objects failure analysis showed under-selection of blocker objects, leading to top-3 and risk-adaptive sparse-evidence backfill experiments.
- Q3 invisible_objects analysis showed many false negatives were absent from the narrow candidate shortlist, motivating broad candidate pools.
- MLP/logistic comparisons showed that the MLP added true positives but also many false positives, motivating rejection of the MLP as a primary selector.

Evaluation Step 7: Ablation Studies
-----------------------------------

Suggested ablations:

- ego-only vs cooperative graph;
- provenance-aware vs provenance-agnostic fusion;
- supported-only vs supported-plus-candidate reasoning;
- visibility-aware vs visibility-agnostic querying;
- narrow vs broad invisible candidate pool;
- heuristic vs risk-adaptive rankers;
- logistic acceptor vs MLP acceptor;
- deterministic KG reasoning vs LLM/reranker variants where available.

12. What The Evaluation Steps Tell Us
=====================================

Q1 notable_objects:

Tests whether visible, path-relevant objects can be selected from the graph. It stresses geometry, trajectory proximity, visibility filtering, and candidate suppression.

Q2 occluding_objects:

Tests whether the graph can identify visible objects that block or occlude other relevant objects. It stresses pairwise relational scoring, blocker identity selection, and sparse-evidence fallback.

Q3 invisible_objects:

Tests whether the system can identify relevant objects that are not visible to the asking vehicle. It stresses visibility labels, candidate pool recall, uncertainty handling, and learned acceptor calibration.

Q4 planning_awareness:

Tests whether the system can combine visible and hidden relevant objects into a planning-aware answer. It stresses task composition and answer-shape alignment.

Q5/Q7 object_motion_prediction:

Tests whether object-track motion can be inferred using adjacent-frame velocity or fallback signals. It stresses temporal graph consistency.

Q6 agent_motion_prediction:

Tests whether other CAV motion can be predicted from pose velocity or planned trajectory. It stresses agent-level temporal context.

Q8 control_settings:

Tests whether graph/planning features can be rendered into action guidance. It stresses task-specific output contracts and planning interpretation.

Q9 future_trajectory:

Tests whether planned trajectory outputs can be rendered and evaluated against trajectory metrics. It stresses trajectory representation and L2-style scoring.


13. Related Work Positioning
============================

Cooperative perception:

F-Cooper, V2VNet, V2X-ViT, and CoBEVT represent the dominant direction of cooperative perception through feature-, message-, transformer-, or BEV-level fusion. These methods motivate the need for V2V cooperation but generally do not expose a symbolic, provenance-aware scene graph for downstream reasoning.

V2V4Real:

V2V4Real provides the real-world two-vehicle cooperative perception setting used by the current work. It is important because it grounds the project in real multi-agent driving data rather than only simulation.

V2V-LLM and V2V-GoT:

These works move cooperative driving toward multimodal LLM reasoning and graph-of-thought prompting. Our approach differs by building an explicit scene knowledge graph as the primary intermediate representation, then performing deterministic graph reasoning. V2V-GoT is also the main benchmark reference for the current QA results.

Knowledge graph reasoning for autonomous driving:

KLDrive is a relevant knowledge-graph-augmented driving QA framework. It supports the broader argument that fact-grounded structured representations can reduce hallucination and improve fine-grained reasoning. Our work differs by focusing on vehicle-to-vehicle cooperative graph fusion, provenance, and visibility/occlusion-aware QA in the V2V-GoT setting.

Occlusion-aware risk:

Occlusion-aware risk assessment and risk-aware motion planning motivate the Q2/Q3/Q4 ranking designs. They support the idea that unseen or partially visible regions should be reasoned about as risk-bearing entities, not ignored.

Important object identification:

Important-object identification literature supports the planning-awareness and notable-object framing: not every detected object matters equally; object relevance depends on trajectory, relations, and driving context.

15. Limitations To State Honestly
=================================

- The current implementation focuses on two vehicles because V2V4Real is a two-vehicle cooperative dataset and because two agents are the minimal setting that exposes cooperative alignment and occlusion recovery.
- Some current high results are from 100-sample slices; final paper claims should use full validation.
- Some official-style evaluation uses a simplified QA-only evaluator path that preserves metric logic but guards missing heavy imports; this should be described clearly if used.
- Q3 invisible_objects remains the most difficult full-validation task and should not be overclaimed until the broadpool logistic policy is validated.
- The current graph fusion is conservative; this improves interpretability but may miss aggressive cooperative recovery opportunities.
- The graph carries confidence channels but does not yet provide a fully calibrated global KG reliability probability.
